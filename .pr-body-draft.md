## What this is

An **opt-in** payment instrument: a guest hands the gate an LNURLcash note
(LUD-25/LUD-26) and the gate redeems it with the note's issuer before granting
access. Disabled by default; an upgrade cannot turn it on.

This is a **draft scaffold being filled in**. It currently contains the config
surface, the activation gate and the decision record. The redemption path, the
durable journal binding and the grant are the follow-up commits on this branch.
I am not claiming any of that works yet — see *Unimplemented at this commit*.

## Design boundary (non-negotiable)

- **Confirmed issuer redemption before access.** Access follows evidence from
  the issuer, not the presentation of a note.
- **Never `cs1` alone.** A certificate with a valid signature and a plausible
  timestamp grants nothing. LUD-25 says a certificate proves the note was
  outstanding at `t`, not that it still is; the previous holder still holds the
  spend.
- **The gate must reach the issuer.** The customer may be offline — they talk to
  the gate over the LAN — but a redemption needs the gate's internet path and a
  reachable issuer. Gate-offline optimistic access is out of scope, deliberately.
- **No issuer keys, no bearer secrets in config or logs.** Spends travel in URLs;
  the gate stores what it has already confirmed, never the secret that proves it.

## Fund-safety invariants this rail must satisfy

Instantiated from `AGENTS.md`; each gets a named test before the code that
depends on it.

| Invariant | Rule |
|---|---|
| Persist before irreversible work | Intent (operation id, client, issuer, `Q`, amount, canonical note URL) is durably bound **before** the redemption request leaves the router. A persistence failure aborts the purchase — it is never logged and ignored (which is exactly what `persistLightningQuotes` does today, and explicitly not the model here). |
| No blind retry after a submit timeout | A redemption whose response never arrived is `unknown`, not `failed`. The gate re-reads the note from the issuer before deciding; re-posting the same spend is how a note is burned twice or stranded. |
| Idempotent grant | Granting is keyed on the operation id and recorded in `paymentjournal`'s `completed` state. A replayed request, a concurrent duplicate and a restart between `paid` and `granted` grant exactly once. |
| One note, one value | A replayed `Q` already recorded paid/burned/pending is refused; the journal additionally refuses a second incoming operation bound to one payment hash. |
| Allowlisted issuers only | Enforced on the canonical host **before** any network call, so a note URL cannot steer the gate at an arbitrary host. |

## Implemented at this commit

- `lnurlcash` config object: `enabled` (default false), `issuers` allowlist,
  `max_note_msat` ceiling, `acknowledgement` version string.
- Activation gate `(*Config).LNURLCashActivation()`: off unless enabled **and**
  the acknowledgement names the version this build presents **and** the
  allowlist is non-empty **and** every entry is a bare canonical host **and**
  the ceiling is non-zero. A router upgraded from any earlier config has no
  `lnurlcash` key and therefore stays off.
- `CanonicalLNURLCashIssuer` + `LNURLCashIssuerAllowed`: one canonicaliser used
  on both sides; URLs, ports, userinfo, IP literals and non-ASCII labels are
  refused rather than silently dropped.
- Decision record `docs/architecture/lnurlcash-rail-decision.md` and the
  changelog fragment.

## Unimplemented at this commit

- **Note decoding.** No `cp1`/`ck1`/`cw1`/`cs1` decoder, no taproot `Q` check, no
  canonical-spend-transaction hash check, no `cs1` verification.
- **The redemption client.** No LUD-25 informational GET, no callback, no
  melt/rotate, no SSRF-hardened transport for this rail (the existing
  `ssrfSafeClient` in `src/lightning/` is a starting point, and its redirect
  handling is not sufficient for the note-URL case).
- **The journal binding.** `paymentjournal` is merged and is the intended store,
  but nothing in this branch calls it; the intent→paid→grant-pending→completed
  path does not exist yet.
- **The grant seam.** No call into `grantAccessForAmount`, no owed-grant /
  retry path for a paid-but-ungranted redemption.
- **The endpoint.** No route is registered. `/ln-invoice` is a Cashu-mint quote
  endpoint and is untouched.
- **Operator UI.** The disclosure is recorded as a version string; nothing
  renders it.
