# T5c re-verification — does cgo + CDK cross-compile for the router arches? (2026-09-19)

**Scope of this file.** `output.txt` (2026-09-14) is the first T5c record; this
file re-runs its central claims on the *pinned* SDK release, replaces the two
summary claims that do not survive re-measurement, and adds the measurements
that were missing (the deployment link, the musl `cdylib`, the patched link).
Every number below is from `./raw/`, which holds the unedited command output.

**Bottom line.** The in-process cgo adapter does **not** link on either router
arch as published — but for **two different reasons**, and on aarch64 the
blocker is a build flag, not an impossibility. Measured verdicts:

| Arch | prebuilt `cdk-go` libs | from-source CDK | verdict |
|---|---|---|---|
| `aarch64_cortex-a53` (arm64) | **fails**: 138 undefined `@GLIBC_2.17…2.34` at link | **builds and LINKS** with 2 patches | **cross-compiles with 2 patches** (was recorded as impossible) |
| `mipsel_24kc` (mipsle softfloat) | **fails**: 691 undefined `ffi_cdk_ffi_*` — no link stanza exists for mips, so no library is passed to the linker at all | Rust half builds (tier-3, nightly `-Zbuild-std`); the **graph fails in `nostr-relay-pool`** on missing `AtomicU64` | **blocked by a dependency** (`nostr-relay-pool` via `nostr-sdk`), not by the arch |

The sidecar recommendation in `01-candidates/cdk.md` is **unchanged** — but the
reason to prefer it is now "2 patches + a 26.5 MB `.so` deployed to a 64–128 MB
router + a `CGO_ENABLED=0`→`1` pipeline rebuild", not "impossible on musl".

## 3. The adapter, per arch — library build green, LINK red (raw/08, 09, 10, 14)

`cd src/tollwallet && go build -tags cdk_wallet ./...` is **exit 0 for both
arches**. It compiles nothing that ships: Go does not perform a final link for a
library package. The same trap exists one level up, where the card warns about
it — `cd src && go build -tags cdk_wallet ./...` is **exit 0** and never touches
the nested module (`raw/05-false-green.txt`).

The deployment link is `src/main.go` → `src/merchant` → `src/tollwallet`
(`src/go.mod` carries `replace …/tollwallet => ./tollwallet`), so this is the
artifact the router would actually run:

## 4. The Rust half: the musl `cdylib` is obtainable (raw/11, 13, 12, 19)

The 2026-09-14 record concluded "musl has no `cdylib`, so the binding's `.so`
contract cannot be met from source". That is **wrong as stated**. Measured with a
minimal crate carrying `crate-type = ["cdylib","staticlib"]`:

```
# default flags, target aarch64-unknown-linux-musl
warning: dropping unsupported crate type `cdylib` for target `aarch64-unknown-linux-musl`
→ libprobe_cdylib.a  23,683,416 B      (no .so at all)

# RUSTFLAGS="-C target-feature=-crt-static"  (dynamic rather than static musl)
→ libprobe_cdylib.so        67,320 B   NEEDED libgcc_s.so.1, libc.so
→ libprobe_cdylib.a  23,683,416 B

# mipsel-unknown-linux-musl, daily nightly + -Z build-std=std,panic_abort, 1m48s
→ libprobe_cdylib.so        66,832 B   ELF 32-bit LSB MIPS32 rel2, NEEDED libgcc_s.so.1, libc.so
→ libprobe_cdylib.a   4,330,474 B
```

The `cdylib` drop is a consequence of musl's `crt-static` default, not a target
limitation: **one flag turns it back on, on both arches.**

### The real thing, built (raw/12, 19)

```
cdk v0.17.3 (482e4df8) — cargo build -p cdk-ffi --release --target aarch64-unknown-linux-musl
  RUSTFLAGS=-C target-feature=-crt-static, CC/AR/linker = OpenWrt 25.12.0 SDK
  rustc = 1.96.0 (cdk's own rust-toolchain.toml pin; its 13-target list has NO
          musl entry and NO mips entry, so the target had to be added per-pin)
Finished `release` profile [optimized] target(s) in 23m 51s     (no errors)

  libcdk_ffi.so        35,021,264 B   unstripped
  libcdk_ffi.so        26,452,880 B   after `openwrt …-strip --strip-all`
  libcdk_ffi.a        170,602,256 B   (162.7 MiB)
  libcdk_ffi.rlib      41,251,572 B
  NEEDED: libgcc_s.so.1, libc.so      (musl — no glibc, no ld-linux)
```

Two facts worth carrying into the decision:

- **Rust `std` cannot be excluded.** The `.so` carries std statically
  (`_RNvCsGIExRX8pES_7___rustc17rust_begin_unwind`, `__rust_alloc` present in the
  symbol table) and CDK's design needs it — `cdk-ffi` depends on
  `tokio` with `rt-multi-thread`, sqlite-via-`rusqlite bundled`, `ring`,
  `secp256k1-sys`, `nostr-sdk`. There is no `no_std` path here; the size is the
  size.
- **Sanity check against the shipped artifact:** the published glibc
  `linux_arm64/libcdk_ffi.so` is 26,518,672 B; our stripped musl build is
  26,452,880 B — within 0.2%. The from-source build is faithful, not a different
  animal.
- Note the `.a` is **162.7 MiB** here, versus 139,601,724 B (133 MiB) recorded on
  2026-09-14. The paths are not byte-comparable: the binding crate's
  `[profile.release]` sets `lto=true, strip=true, codegen-units=1` while the
  monorepo workspace build used for this run does not, so treat both `.a` numbers
  as "roughly 130–160 MiB of Rust archives", not as a regression.

## 5. The patched link — measured, not extrapolated (raw/18)

Applying the two patches to a throwaway copy of the module (module cache is
read-only) and re-linking the service:

```
P1  produce the musl object with -C target-feature=-crt-static
P2  put that object where bindings/cdkffi/link_linux_arm64.go expects it
    (native/linux_arm64/libcdk_ffi.so) — via a fork/vendor/replace of cdk-go

$ go build -tags cdk_wallet   (aarch64 musl, patched)      exit=0
PRODUCED: 18,033,248 B   (baseline without the tag: 16,770,936 B → the adapter costs +1,262,312 B)
  NEEDED   libcdk_ffi.so
  NEEDED   libgcc_s.so.1
  NEEDED   libc.so
  RPATH    /home/c03rad0r/worktrees/t_7a133499/cdk-go-musl/bindings/cdkffi/native/linux_arm64
  interpreter /lib/ld-musl-aarch64.so.1
```

So aarch64 **does** cross-compile in-process with cgo — and the runpath lands in
the *build machine's* module cache, which is the packaging landmine already
noted in `01-candidates/cdk.md` §B2, now confirmed for the musl path as well.
That is patch **P3** (rewrite the runpath / install the `.so` at a stable path /
set `LD_LIBRARY_PATH` in the init script), plus a **26.5 MB** runtime artifact on
the router for a device class with 64–128 MB RAM and 16–32 MB flash.

`mipsel` has no `link_*` stanza to patch: it needs a new one, and a Rust build of
the whole graph for a tier-3 target — see §6.

## 6. mipsel: the arch is workable, the dependency is the question

Measured:
- `rustup target add mipsel-unknown-linux-musl` → **exit 1**: *"toolchain
  'stable-x86_64-unknown-linux-gnu' has no prebuilt artifacts available for
  target 'mipsel-unknown-linux-musl' … may happen to a low-tier target"*
  (tier 3 — `-Z build-std` is mandatory, nightly only).
- With nightly `-Z build-std=std,panic_abort` and `-crt-static` off, a minimal
  MIPS `.so` **is** produced (66,832 B, `raw/13`), so the toolchain and std are
  not the wall.
- `cargo tree -p cdk-ffi --target mipsel-unknown-linux-musl` shows the graph
  contains `nostr-relay-pool v0.44.1`, `nostr-sdk v0.44.1`, `ring v0.17.14`,
  `secp256k1-sys v0.10.1`, `libsqlite3-sys v0.28.0`, `rusqlite v0.31.0`. The
  2026-09-14 sidecar run pinned the mipsel failure on
  `nostr-relay-pool` needing `std::sync::atomic::AtomicU64`, which
  `mipsel_24kc` (no 64-bit atomics) does not provide.
- **Full-graph result for `cdk-ffi` on mipsel — MEASURED, and it is a hard
  dependency blocker.** `cargo +nightly check -Z build-std=std,panic_abort
  --target mipsel-unknown-linux-musl -p cdk-ffi` (254 crates checked, then):

  ```
  error[E0432]: unresolved import `std::sync::atomic::AtomicU64`
   --> …/nostr-relay-pool-0.44.1/src/relay/flags.rs:8:25
  8 | use std::sync::atomic::{AtomicU64, Ordering};
    |                         ^^^^^^^^^ no `AtomicU64` in `sync::atomic`
  … also src/relay/ping.rs:6, src/relay/stats.rs:7
  error: could not compile `nostr-relay-pool` (lib) due to 3 previous errors
  EXIT=101                                  (raw/20-mipsel-cdkffi-check.txt)
  ```

  `nostr-relay-pool` arrives through `nostr-sdk`, which CDK pulls in for its
  **default** features (`npubcash`, `nwc`). `mipsel_24kc` has no 64-bit atomics,
  so `std` omits `AtomicU64`. This is the same wall the 2026-09-14 sidecar run hit
  — it is **not** specific to `cdk-cli`: the in-process path inherits it, because
  `cdk-ffi` needs those Nostr crates too. It is a *dependency* fix (a
  wallet-only feature set that drops `nostr-sdk`, or `portable-atomic` shimming
  upstream), not a compiler flag.

The Go-side half of mipsel is not blocked by any of this: the *service* links
clean for mipsle musl (18,073,276 B). It is the CDK dependency graph that decides
mipsel, exactly as the 2026-09-14 sidecar finding said — and it applies to the
in-process path too, because `cdk-ffi` pulls the same `nostr-*` crates that
`cdk-cli` does.

## 7. Verdicts, and what each one costs

1. **aarch64 (arm64, the arch the wallet baseline was measured on):
   cross-compiles with 2 patches** (P1 `-crt-static`, P2 musl `.so` in the
   binding's expected path), plus P3 the runpath/packaging work and P4 the CI
   change from `CGO_ENABLED=0` to a per-arch cgo cross-toolchain
   (`build-package.yml:181`). Cost beyond the patches: +1.26 MB in the binary and
   a 26.5 MB `.so` at runtime.
2. **mipsel/mips: not buildable as published and not buildable from source
   either, on the current dependency graph.** The binding has no mips/mipsle link
   stanza (measured, 691 undefined symbols), the target is Rust tier 3, and the
   full graph fails in `nostr-relay-pool` (`AtomicU64`, measured above). mipsle is
   **7 of the 17 CI matrix rows**; fixing it means an upstream dependency change
   (drop `nostr-sdk` from the default feature set, or `portable-atomic`), not a
   build flag. armv7 (`arm_cortex-a7`) is another arch with no `cdk-go` artifact
   and no measurement here at all.
3. **The sidecar remains the cheaper architecture** — it keeps
   `CGO_ENABLED=0`, needs no patched binding, no musl `.so` deployment, and
   already measures clean on the physical MT6000 (19.7 MiB static `cdk-cli`,
   ~5.6 MB peak RSS, 5 threads; `../cdk-sidecar/`). The only thing this
   re-verification removes is the word "impossible" from the in-process column.

## 8. What this file does NOT establish (boundary of the measurement)

- Nothing was **executed on a router**: the aarch64 patched binary and the musl
  `.so` are shown to *link* and to carry musl `NEEDED` entries; no `dlopen`, no
  wallet call, no RSS/thread figure for the in-process path. Those remain
  on-device work (`03-*`/T1a style measurement).
- No mips/mipsle **full build** is claimed: the mipsel result is a `cargo check`
  (type-check, no codegen) that fails in `nostr-relay-pool` before any link. The
  arch itself is proven workable only to the minimal-cdylib probe (`raw/13`).
- `arm_cortex-a7` (armv7) was not measured at all.
- The `.a`/`.so` sizes are from the monorepo workspace profile, not from cdk-go's
  own `[profile.release]`; sizes are indicative, the *link* results are not.
