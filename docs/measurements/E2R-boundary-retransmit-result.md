# E2-R — retransmission / double-count at the tunnel-side boundary

**Status: FAIL (borderline, no-loss cell). One sub-claim REFUTED, one design premise REFUTED.**
**Experiment: `EXP-CONSULTANT.md` §1 "Q2 (LOAD-BEARING)".** Run 2026-10-17.

This is the architecture gate. Nothing is billed until it is green, and it is not green.

## Verdict, up front

| Sub-claim | Threshold (frozen in `EXPERIMENT-CONSULTANT.md`) | Measured | Verdict |
|---|---|---|---|

**Decision-table row selected (`EXP-CONSULTANT.md` §4):**

> **`R > 0.02` with no loss injection → "the meter counts something that is not the datagram stream
> (key overlap, two rules, the proxy's own internet leg leaking into the rule) → STOP. Fix the rule
> placement first and re-run before any interpretation."**

That row is a STOP, and it is the correct reading: a healthy, loss-free path shows a **3.2%**
inflation, which is larger than the 2% budget. Two candidate explanations are live and the
experiment does not distinguish them (see "What this does not settle"), so the honest action is to
**not proceed to billing** and to fix/diagnose the rule placement first.

## Method, and the precondition

- **P0–P6 independence precondition: PASS.** `ip route get` over *both* peer addresses resolved to
  **different egress interfaces** (`a0` vs `b0`) **and different source addresses**
  (`10.10.1.1` / `10.20.2.1`). `MPJoinSynRx`/`MPJoinAckRx` = **3/3** at the responder — a subflow can
  only form if that counter moves, and it moved. The topology traps were honoured: both ends
  registered endpoints as **`signal subflow`** (a `subflow`-only endpoint never sends `ADD_ADDR`).
- Harness: `e2r-boundary-retransmit.sh` (committed alongside this result). Two netns, two veth pairs,
  `tbf` + `netem` per leg, `IPPROTO_MPTCP` (262) sockets both ends, a **measurement-only**
  accept-policy counter chain at the server's tunnel side.
- n = **5** runs per cell, three cells: `golden`, `noloss`, `loss` (5% on the carriage leg).
- Payload per run: 256 MiB. Plaintext is known exactly from the generator's own count
  (`cli_sent`), which is the arbiter — never the meter.
- `R` = (boundary count − plaintext) / plaintext. `D` = (legA + legB − boundary) / boundary.

## The two refutations (these change the design, not just a parameter)

**R1 — `D` is a tautology at a single boundary, so the "naive per-path meter double-counts" premise
is not realizable as stated.** `D = (legA + legB − boundary) / boundary ≡ 0.000000` in all 15 runs,
including under loss. That is not a measurement result: the boundary rule and the two per-leg rules
count the **same packets** at the **same hook**, so `boundary ≡ legA + legB` **by construction**. The
quantity the design was worried about cannot be observed at a single convergence point — only `R`
(the retransmit/framing inflation against known plaintext) carries information. **Consequence: the
"per-path vs tunnel-side" framing is not a choice the meter makes; at one boundary there is only one
number.** The real question is narrower and is exactly `R`: does a **retransmission generated by the
far side** of the boundary get counted again when it crosses back?

**R2 — where the loss is injected decides whether the experiment tests anything.** An n=1 smoke run
with loss on the *idle* leg produced `shareB = 0.0088` and an uninformative `R = 0.020`; the same
size with loss on the *carriage* leg produced `shareB = 0.343` and `R = 0.236`. The harness therefore
carries a **validity gate** — if the impaired leg carried `< 1%` of payload, the run is reported
`INVALID_no_traffic_on_lossy_leg`, never PASS. Without that gate a run that never exercised the
impairment reads as a clean no-loss result. The committed harness has this gate; the earlier
investigation in this project did not.

## What this does NOT settle (so it is not over-read)

1. **Whether the 3.2% no-loss inflation is the meter counting the wrong thing, or is real
   encapsulation overhead at this boundary.** In this lab the boundary is a plain netfilter counter
   with **no proxy in the loop** — so there is no Shadowsocks encryption or framing to explain 3.2%.
   That makes "the meter counts something else" the leading hypothesis, which is precisely why the
   decision table says STOP and fix rule placement before interpreting.
2. **The magnitude on the real path.** `EXP-CONSULTANT.md` §5 is explicit that the *number* requires
   the real server with the real proxy and a genuinely lossy independent leg; this run is the
   **mechanism** in the netns lab. Both the no-loss 3.2% and the loss-cell spread
   (1.95%–6.71%, i.e. ~3.4× variation across 5 runs) must be re-taken there.
3. **Whether the far-side-generated retransmission is the mechanism.** The loss cell's mean `R`
   (3.53%) is barely above the no-loss mean (3.16%), which is **not** what a naive "retransmits are
   billed twice" model predicts at 5% loss — and the loss cell's per-run spread is wide
   (1.95%–6.71%). Confirming the mechanism needs a `tcpdump`-on-both-legs comparison against the
   per-leg counters, which this harness runs but which is not yet reduced.
4. **The per-leg RTT actually achieved.** `netem` was configured but the achieved RTT is not
   published in this record — a gap the consultation flagged. The split moved from ~46% to ~90% on
   leg B under loss, which is consistent with the scheduler preferring the healthy leg, but the RTT
   is the missing datum.

## Consequence for the programme

Per the prompt and the decision table:

- **The loop does not bill. The system stays ADVISORY-ONLY** (which is also the standing rule until
  the crash-durability question is green).
- **The unconditional change (i) still applies and is *strengthened*** — the correctness claim is
  rewritten as *"the rule key matches every subflow of a client"*, and the N ∈ {1,2,4} regression
  test is now the vehicle for the rule-placement diagnosis this result demands.
- **The unconditional change (ii) still applies** — durable journaling before any enforcement.
- **The design does not proceed to pricing** until `R`'s no-loss component is attributed on the real
  path.

## Reproduce

```
sudo E2R_RUNS=5 E2R_BYTES_MB=256 E2R_SLOW_DELAY_MS=60 E2R_LOSS_LEG=a \
  bash e2r-boundary-retransmit.sh
```

Every threshold above is a variable in the harness (config-as-code), not a hardcoded constant:
`E2R_LOSS_PCT`, `E2R_LOSS_LEG`, `E2R_RUNS`, `E2R_BYTES_MB`, `E2R_PACE_MBIT`, the per-leg netem
delays, and the leg subnets. The raw record is written to `E2R_OUT` (default
`/home/c08r4d0r/reports/mptcp-loop/e2r-raw.txt`, absolute because under `sudo` `$HOME` is `/root`).
