# RESOLVED 2026-09-23 -- portal:lightning-lane-against-live-module
#
# The entry that used to be here recorded that the captive portal's Lightning
# lane could not buy time from the module as shipped, observed on
# v0.6.0-alpha4-pre15 x86_64:
#
#   portal POSTs /ln-invoice          body {"amount":210,"mint_url":"http://…"}
#   module 400 {"error":"failed to create lightning invoice"}
#   module log: error="mint does not exist"
#
# The portal echoes the mint URL from the advertisement's price_per_step tag,
# which is the configured accepted_mints[].url verbatim (the shipped default
# config writes it without a trailing slash), while the wallet registers and keys
# a mint in canonical form ("<url>/") and the module passed the caller's
# mint_url through unchanged -- so the lookup could not match. The 2x2 matrix
# over {config with/without slash} x {request with/without slash} showed only
# requests carrying the slash succeeding, regardless of the config form: a
# default install could not sell via the Lightning lane at all. The Cashu lane
# was unaffected (it never takes a mint URL from the client), which is why a
# manual token-paste pass on pre15 hid it.
#
# Fixed in pr/mint-url-normalisation: the module canonicalises the
# client-supplied mint URL at the boundary where it enters
# (tollwallet.NormalizeMintURL, the same function that produces the registry
# keys), so both spellings of one mint resolve to the single registered entry.
# The check now passes on a branch-built artifact with the client identity
# resolvable; see README "Known issues" for the harness precondition that the
# live-module lane needs and how it was verified.
#
# No entry below: this file currently tolerates nothing.
