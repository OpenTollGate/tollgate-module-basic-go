# Durable Lightning operation journal

A bounded single-writer journal for payment intents, payout reservations and purchase-grant progress. It does not send funds or grant network access and does not alter the existing Cashu store.

`Open` requires a dedicated owner-only directory and exclusively locks its writer file. The directory must be a persistent canonical path with no symlinked ancestors and a `0700` leaf owned by the effective uid; journal files are `0600` regular files with link count one. On OpenWrt, `/tmp` is commonly volatile and `/var` may resolve there. Check the target's mounts and symlinks, select a canonical persistent location, and verify that it survives reboot; this package does not provision that storage. After acquiring the flock, the writer verifies the locked descriptor still matches a fresh identity check of `writer.lock`, and revalidates that identity before every later mutation; a replaced or removed lock file poisons the writer instead of mutating without the single-writer guarantee. The next writer simply opens and locks whatever valid file is at the path — there is no unlink-based recovery. Snapshots are protected `0600` files, atomically replaced with file and parent-directory fsync. Linked, foreign, malformed, duplicate-key, unknown-field, unsupported-format or oversized data is refused. Required I/O failure poisons the open writer; close, reopen and reconcile before further work. Existing source state is retained rather than overwritten after an outside edit.

Recovery, transitions and invoice binding keep each operation's update timestamp at least as recent as its stored timestamps. A backward clock step or pre-NTP reboot cannot make the next reopen reject an otherwise valid operation. Version/CAS controls ordering; timestamps are audit metadata.

`Prepare` binds a stable operation ID to wallet, amount, direction, recipient and opaque noncredential request data. It idempotently returns the same operation but refuses rebinding. Outgoing principal/fee reservations are serialized against the selected wallet/period budget. Unknown outcomes remain reserved across period boundaries. Completed successes use actual fees; definitive failure releases only that operation's reservation. Keep different aliases of the same treasury in the same wallet budget domain.

For outgoing payments, `SubmitOutgoing` with the **current** period budget is the only submission route: `Advance` refuses the outgoing `prepared → submitted` transition outright. `SubmitOutgoing` persists `submitted` before the external monetary request and atomically rechecks all reservations and in-period actual costs, counting the prepared operation once; a budget tightened after `Prepare` is enforced at submission. An idempotent `Prepare` return records intent; it does not authorize a send under an old budget. Callers must also recheck current consent, per-payment limits, invoice expiry and provider policy before submission — authorization happens entirely before the send. `Advance` remains the CAS transition API for incoming submission and for reconciliation and terminal outcomes; it performs no current-budget check.

After restart any unreconciled submitted record becomes `unknown` and cannot be resubmitted through the state machine. Resolve unknown outcomes against the authoritative wallet; never infer failure from a timeout. An incoming invoice is bound once before exposure; paid/grant-pending/completed progress cannot be rewound to replay a credit. Exact idempotent application of the grant is the caller's responsibility, as is validating provider settlement and deciding that a failure is definitive.

Actual fees are accounted truthfully after the send: a verified settlement fee above the pre-send reservation is recorded as spent even though it exceeds `FeeReserveMSat`, and later payments are refused once the period budget is actually exhausted. The reservation is a pre-send headroom check, never a retroactive permission to suppress a verified expense or manufacture false headroom. Callers must authenticate and verify settlement before recording it, and enforce an available hard cap before any external send.

Operation bytes are sensitive plaintext at rest inside the protected `0600` files — the journal does not encrypt its contents, so the directory's ownership and mode are the confidentiality boundary. Store prepared encrypted NWC events or nonsecret invoice parameters: never API keys, NWC connection URIs, wallet private keys, or standalone preimages not required by an operation in flight. A valid BOLT11 invoice's `payment_secret` is legitimate protocol data and may be stored as part of that invoice. Caller-controlled time/pricing/policy/grant snapshots must be recorded before irreversible work. This journal is a local transaction primitive, not an atomic transaction with a remote wallet or NDS, and does not make legacy session metering durable.

From `src`: `go test -race -count=1 ./paymentjournal`, `go vet ./paymentjournal`. Tests exercise concurrent reservations/CAS, restart, partial recipient success, malformed/foreign/unknown-field/oversize snapshots, real child-process exits before/after atomic rename (exact helper exit codes) and after submitted state, SIGKILL after a prepared intent is durable, with that intent preserved and the flock released for the next writer, and replacement of `writer.lock` refusing further mutation. Test fault injection replaces the store's rename operation; there is no production crash environment variable.
